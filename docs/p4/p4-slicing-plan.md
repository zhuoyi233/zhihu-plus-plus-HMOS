# P4 创作与媒体执行计划

> 制定日期：2026-08-20  
> 范围：P4（创作与媒体，预计 3–5 周）的可执行切片、依赖顺序与验收门禁  
> 工具链：HarmonyOS API 26 编译，`targetSdkVersion` / `compatibleSdkVersion` 均为 6.1.1（API 24）  
> 起始测试基线：51 个套件、Hypium `404/404`  
> 当前进度（2026-08-20）：P4-0 已完成；P4-1 安全草稿、P4-5 播放状态机、P4-6 扫码确认和 P4-7 分享安全边界已完成首个可验证切片。当前测试基线：57 个套件、Hypium `436/436`；P4-2、P4-3、P4-4 与 P4-8 待开始
> 行为基线：Android Lite 的 `WriteAnswerScreen`、`WritePinScreen`、`ZhihuAnswerPublisher`、`ZhihuPinPublisher`、`ZhihuImageUpload`、`VideoPlayerActivity` 与 `QRCodeScanActivity`

## 1. 阶段目标与边界

P4 把当前“以阅读和社交互动为主”的应用扩展为具备基础创作和前台媒体能力的客户端。阶段完成后，登录用户应能安全恢复草稿、发布或编辑回答、发布想法并上传图片；所有用户应能播放受支持的视频、完成电脑端登录扫码确认，并通过系统分享文本、图片和应用拥有的文件。

P4 必做范围：

- 写回答、编辑自己的既有回答；
- 写想法；
- 本地草稿恢复与受控的知乎远端草稿同步；
- 系统图片选择、格式校验、压缩/尺寸治理和知乎图片上传；
- 前台视频播放；
- 将 P0 Scan Kit 原型收敛为生产扫码入口；
- 文本、图片和应用文件的系统分享；
- 系统 TTS 可行时提供前台朗读，否则形成明确的后置结论。

明确不进入 P4：

- 写文章、提问题、发布视频或编辑既有想法；
- Markdown、HTML、长图和 PDF 导出，这些仍属于 P5；
- 视频下载、截图、画中画、后台播放和 AVSession；
- 自定义相机扫码界面；默认继续使用 Scan Kit 系统界面，不申请相机权限；
- AI 总结、端侧 NLP、模型和推理依赖；
- 自动化测试向知乎生产环境发布真实内容；
- 为迁移 Android UI 而引入整页 ArkWeb 编辑器。ArkWeb 只允许用于知乎登录/风控和受限扫码确认。

## 4. P4-0 合同冻结与平台边界（已完成）

### 范围

先冻结创作协议和窄平台接口，不在本切片制作完整页面：

- `core` 增加强类型目的地和草稿身份：回答以 `questionId` 为目标，可选 `answerId`；想法使用本地稳定 UUID；
- `data` 定义 `AnswerPublishRepository`、`PinPublishRepository`、`ImageUploadRepository`，页面不得直接拼接 URL、Cookie 或发布 JSON；
- `entry/platform` 定义 `ImagePicker`、`ShareService`、`QrScanner`、`MediaPlaybackService` 和可选 `SpeechService`；
- 将 Android 上游请求、脱敏响应和异常响应固化为 fixtures/golden，不直接复制 Kotlin 类型；
- 所有外部 JSON 继续经过有界名义 AST 或显式 decoder，禁止 `JSON.parse` 后结构赋值；
- 发布错误统一映射为认证失效、风控/权限拒绝、限流、内容校验、冲突、网络、超时、取消和服务端错误。

### 必须冻结的接口合同

回答：

1. 查询 `api.zhihu.com/questions/{questionId}` 的 `relationship.my_answer`，判断新建还是编辑；
2. 回填已有回答的 `editable_content`，缺失时回落 `content`；
3. `POST www.zhihu.com/api/v4/questions/{questionId}/draft` 保存知乎远端草稿；
4. `POST www.zhihu.com/api/v4/content/publish`，`action=answer` 发布或更新；
5. 成功响应的 `data.result` 是第二层 JSON 字符串，必须再次有界解析获得回答 ID；错误码 `103003` 作为“已有回答冲突”单独处理。

想法：

1. `POST api.zhihu.com/content/publish/topics/recommend` 获取话题建议；
2. `POST api.zhihu.com/content/drafts`，`action=pin` 保存远端草稿；
3. `POST www.zhihu.com/api/v4/content/publish`，`action=pin` 发布；
4. title、hybrid HTML、media 和 topic 使用想法专用 payload，不与回答发布器复用。

所有写请求必须使用已认证会话、精确受信主机、固定路径构造、`maxRedirects=0`、ZSE 和需要时的 `_xsrf`；Cookie、响应原文、编辑内容和 OSS 临时凭证不得进入日志。

### 自动化与退出条件

- URL、方法、header、重定向、请求体和双层响应解析均有黄金测试；
- 内容 ID、问题 ID、回答 ID、话题 ID和本地草稿 ID都有长度与格式门禁；
- 401/403/429/5xx、取消、超时、非法 JSON 和重复发布冲突有固定错误映射；
- 平台能力只通过窄接口进入页面，组合根可以注入 fake；
- 不发送任何真实发布请求即可通过本切片全部测试。

## 5. P4-1 编辑器与安全草稿

### 数据与持久化

- RDB 从 v4 连续迁移至 v5，新增 `content_drafts` 元数据表；迁移必须事务化，失败原子回滚，不允许删除重建；
- 草稿键至少区分账号、类型和目标：`answer:{account}:{questionId}`、`pin:{account}:{localUuid}`；账号部分使用稳定标识的不可逆摘要，不使用 Cookie；
- RDB 保存草稿类型、目标 ID、远端内容 ID、标题、纯文本长度、目录开关、图片/话题引用、dirty 状态、版本和时间戳；
- 正文 HTML 写入应用沙箱的加密草稿信封，密钥使用独立 Asset Store alias，不与 Session Cookie 密钥混用；
- 使用临时文件写入后原子替换。正文、原始图片字节和 OSS 凭证不得写入日志、Preferences 或导出备份；
- 登出不静默删除草稿；切换账号后只显示当前账号草稿。用户显式丢弃时删除元数据、正文信封和未引用临时图片。

### 编辑状态

- `EditorController` 统一持有加载、编辑、预览、本地保存、远端同步、发布、错误和离页确认状态；回答/想法只组合各自字段，不复制生命周期逻辑；
- 本地自动保存使用 1500 ms debounce，应用切后台、页面离开和发布前立即 flush；
- 迟到保存结果以递增 generation 拒绝回写，新内容不能被旧保存覆盖；
- 草稿按编辑目标恢复，不允许关闭一个编辑器后把内容带到另一个问题或另一账号；
- 编辑器首版只承诺知乎发布所需的安全 HTML 子集、图片占位和原生预览，不实现完整桌面富文本排版；
- 关闭存在未保存修改的编辑器必须提供“继续编辑 / 保存草稿并退出 / 丢弃”三种明确动作。

### 自动化与退出条件

- v4 → v5 migration、关闭重开、写入中断、损坏信封、账号隔离和删除清理有测试；
- debounce、立即 flush、generation、并发保存、离页确认和恢复目标有状态机测试；
- 强制停止进程后能恢复同一草稿；升级安装后草稿仍可恢复；
- 编辑预览只走现有原生 Reader AST，不把正文交给整页 ArkWeb；
- 文档和日志不含草稿正文、账号 Cookie 或加密密钥。

## 6. P4-2 图片选择、处理与上传

### 本机处理

- 优先使用系统 Photo Picker，只获得用户选中的文件，不申请相册全量读取权限；
- 输入流必须有明确的单文件、总批次、像素和解码内存上限。具体数值在 P4-0 的 API 24 真机基线后冻结为常量并写入验证文档；
- 通过 magic bytes 与实际解码结果识别 JPEG、PNG、WebP、GIF，不能只信扩展名或 MIME；
- JPEG/PNG/WebP 的方向修正、缩放和压缩放入 TaskPool；GIF 保持动画语义，不能无提示压成静态首帧；
- 临时文件位于应用 cache，草稿只持有受控文件引用；成功上传、取消编辑和过期清理都要释放 PixelMap、文件句柄与临时文件；
- 上传前展示预览、尺寸、大小和删除入口，用户取消选择不产生网络请求。

### 知乎上传协议

对齐 Android Lite/zhihu_obsidian 的三段流程：

1. 计算 MD5，`POST api.zhihu.com/images` 申请 `image_id` 与临时 `upload_token`；
2. 非 GIF 使用 `PUT zhihu-pics-upload.zhimg.com/v2-{hash}`；GIF 使用 1 MiB 分片初始化、上传和完成协议；
3. 通知 `uploading_status`，再轮询 `GET api.zhihu.com/images/{imageId}`，成功后只接受受信知乎图床的 `src/original_src/watermark_src`。

OSS access id、access key、security token 和 Authorization 只存在于单次上传对象内；禁止写入 RDB、草稿、日志和测试报告。上传主机、路径、签名串、日期格式、ETag、XML 和轮询次数必须有纯函数/Mock HTTP 测试。MD5 与 HMAC-SHA1 仅用于协议兼容，不作为本地安全校验算法。

### 自动化与退出条件

- 格式嗅探、尺寸解析、旋转、压缩边界、超限拒绝、取消和临时文件清理有测试；
- 单 PUT、GIF 分片、ETag 缺失、轮询成功/超时、服务端复用已有图片和非法图床 URL 有合同测试；
- 进度只显示已选择、处理中、上传中、完成、可重试失败和已取消，不展示上游响应原文；
- API 24 真机至少验证 JPEG、PNG、WebP、GIF、超大图片、权限取消、断网和切后台恢复；
- 发布失败后已上传图片仍保留在草稿引用中，不要求用户重复选择和上传。

## 7. P4-3 回答草稿、发布与编辑

### 产品链路

入口位于问题详情“写回答”和自己的回答详情“编辑”。未登录时只进入登录 CTA，不创建空草稿或发请求。

发布顺序固定为：

1. 校验 questionId、登录态、正文和编辑目标；
2. flush 本地草稿；
3. 完成正文内待上传图片并生成受信 HTML；
4. 写入知乎问题草稿；
5. 调用 `content/publish`；
6. 解析发布后的 answerId，跳转回答详情并刷新问题关系；
7. 确认服务端成功后才把本地草稿标记为已发布并清理正文信封。

本地草稿高频保存，远端草稿最多每 30 秒同步一次，并在切后台/显式保存时尝试同步；断网时本地保存继续成功。若已有回答，先加载 `editable_content` 和目录开关；本地草稿比远端回填新时不得被覆盖。

### 状态与错误

- 发布按钮在请求进行中禁用，禁止重复提交；离页取消只阻止 UI 回写，不宣称已经撤销服务端可能完成的发布；
- 401 进入登录恢复；403/风控保留草稿并提供受限验证入口；429 显示稍后重试；103003 重新查询自己的回答并提供转入编辑；
- 所有失败路径保留本地草稿和已上传图片；只有明确成功才导航和清理；
- 不把上游 message、HTML、问题标题、Cookie 或请求体拼入日志与用户错误提示。

### 自动化与退出条件

- 新回答、编辑回答、目录开关、双层成功响应、重复回答、失败保留和迟到响应均有测试；
- Mock HTTP 断言草稿和发布两步请求的顺序、header、payload 与重定向边界；
- 专用测试账号在 API 24 设备完成一次文本回答发布、一次带图回答发布、一次编辑并重启恢复；
- 真实发布前有预览和最终确认，测试产生的内容 ID记录在脱敏验收文档中，不记录 Cookie。

## 8. P4-4 想法草稿与发布

### 产品链路

- 支持可选标题、正文、图片和话题；至少一项内容非空才允许保存远端草稿或发布；
- 话题查询 debounce、可取消、分页/数量有界；选择的话题同时进入展示 marker 和发布 payload；
- 想法的 HTML、`textLength`、media 尺寸/URL和 topic payload 由专用 builder 生成；不能把回答请求体改字段后复用；
- 本地草稿、远端 `content/drafts` 和正式 `content/publish` 分开显示状态；远端草稿失败不破坏本地草稿；
- P4 只发布新想法，不承诺编辑已经发布的想法。

### 自动化与退出条件

- 空内容拒绝、标题/正文/纯图片、话题去重、HTML 文本长度和 media payload 有黄金测试；
- 话题推荐的 query 编码、迟到响应、失败回退和离页取消有测试；
- 保存远端草稿、发布、双层 ID 解析、401/403/429 和失败保留有 Mock HTTP 测试；
- API 24 设备完成文本想法、带图想法、带话题想法和强制停止后的草稿恢复；
- 发布成功进入原生想法详情，返回列表后能刷新看到新内容。

## 9. P4-5 前台视频播放

### 范围

- 为现有 `P1DestinationName.VIDEO` 接入真实页面和视频详情/播放源 decoder；
- 使用 Media Kit AVPlayer，状态机覆盖 idle、preparing、ready、playing、paused、completed、error 和 released；
- 首版提供播放/暂停、进度、拖动、全屏、加载和重试；进入后台或音频焦点丢失时暂停；
- 页面销毁必须解绑回调并 release，迟到回调不能修改已离开的页面；
- 播放 URL、重定向和自定义 header 使用独立受信策略；Cookie 只允许发往冻结后的知乎/视频 CDN 主机。

不在本切片实现后台播放、画中画、锁屏控制、下载、截图、倍速或投屏。这些能力需要额外权限、AVSession、长时任务或文件治理，单独后置。

### 自动化与退出条件

- 视频响应 fixture、清晰度选择、URL 白名单和空源/过期源有 decoder 测试；
- AVPlayer 通过 fake adapter 测状态迁移、seek、重试、前后台暂停和 release 幂等；
- API 24 设备验证 MP4/HLS（以真实接口返回为准）、旋转/全屏、来电或切后台、弱网和播放结束；
- 连续进入退出 20 次无残留播放、重复回调或明显资源增长。

## 10. P4-6 生产扫码闭环

### 两种二维码方向继续分离

1. **本机显示二维码供其他设备扫描**：P2 已由 `ZhihuQrLoginClient`、登录页和风控 ArkWeb 完成，P4 只做回归，不重写；
2. **本机扫描电脑端登录码**：把 `QrScanProbePage` 收敛成生产 `QrScanner` 和登录入口。

生产扫描只允许 Scan Kit `QR_CODE` 单码结果，并复用 `QrLoginScanPolicy`：HTTPS、精确 `www.zhihu.com`、精确 `/account/scan/login/{token}`、无 userinfo/端口/重复分隔符。识别成功后先展示固定来源和明确的“确认登录电脑 / 取消”，绝不因识码成功自动提交确认。

P4-0 应先探测专用确认请求是否有稳定合同；若无法完整冻结 CSRF、风控和成功判定，默认使用受限 ArkWeb：只加载已校验登录 URL，注入会话 Cookie 仅限精确主机，禁止任意导航和外部 scheme，使用默认移动 UA，并复用现有风控页。扫描 token 和原始 URL不得展示、持久化或记录。

### 自动化与退出条件

- 策略矩阵补齐过长 token、编码绕过、相似域名、重定向和重复提交；
- fake scanner 覆盖成功、取消、服务不可用、前后台切换和重复点击；
- API 24 真机验证对焦、暗光、相册识码、取消和电脑端确认成功；
- 默认系统扫码仍不新增 CAMERA 权限；如未来改自定义扫码，必须退出本切片重新做权限和隐私评审。

## 11. P4-7 系统分享收口

### 范围

建立统一 `SharePayload` 和 `ShareService`：

- 文本：标题、摘要和受信内容链接；
- 图片：已下载的应用临时图片或受信图片 URL；需要二进制分享时先下载到受控 cache；
- 文件：只分享应用创建且位于允许目录的文件 URI，文件生成本身仍由其他阶段负责；
- 分享取消视为正常返回，不显示失败；没有处理方、文件丢失和权限拒绝显示固定文案。

系统分享不得携带 Cookie、Authorization、自定义请求头、正文 HTML 或内部路径。临时分享文件使用唯一名称和受限生命周期，成功拉起分享面板后延迟清理；不能把任意用户输入路径交给分享 Want。正文图片现有“分享 URL”升级后仍保留安全回退。

### 自动化与退出条件

- 三类 payload、MIME、标题、URI 范围、超限文本、非法路径和无处理方有测试；
- 回答、文章、问题、想法、用户主页和正文图片使用同一服务；
- API 24 设备验证至少两个系统分享目标、取消、图片二进制和应用临时文件；
- 分享完成或过期后临时文件可回收，不影响原始草稿和相册文件。

## 12. P4-8 可选系统 TTS

P4-8 先做可行性门禁，不默认承诺交付。只有 API 24 设备上的系统语音能力、中文质量和生命周期均稳定时才进入产品实现：

- 输入来自 Reader AST 的纯文本，不直接朗读 HTML、公式 URL、图片 URL 或隐藏节点；
- 长正文分段排队，支持播放、暂停、继续、停止和段落进度；
- 离开页面和应用进入后台默认停止，不申请后台长时任务；
- 语音服务需要联网或上传文本时，必须先补隐私说明和用户开关，默认关闭；
- 不把文章正文写入日志、缓存报告或第三方分析。

若 API 24 不具备稳定接口，交付 `docs/p4/p4-8-tts-feasibility.md` 的后置结论即可，P4 仍可完成。

## 15. 风险与处置顺序

| 风险 | 等级 | 处置 |
| --- | --- | --- |
| 发布/草稿接口变化或风控 | 极高 | P4-0 冻结真实合同；失败保留本地草稿；真实写入只人工验收 |
| OSS 临时凭证泄露 | 极高 | 仅内存、日志脱敏、禁止重定向、精确主机、fake/Mock 测试 |
| 草稿因崩溃、切号或发布失败丢失 | 极高 | 加密信封、原子写、账号隔离、generation、成功后才清理 |
| 大图/GIF 导致内存峰值或卡顿 | 高 | 有界输入、TaskPool、分块处理、PixelMap/临时文件显式释放 |
| API 26 编译掩盖 API 24 不可用调用 | 高 | API 起始版本审计、`apiAvailable` 防护、API 24 设备为必过门禁 |
| AVPlayer 生命周期泄漏 | 高 | 窄 adapter、状态机、离页 release、连续进出压力测试 |
| 扫码结果被用于任意导航 | 高 | 纯 ArkTS URL 策略、用户确认、受限 ArkWeb/固定协议 |
| 分享泄露 Cookie、内部路径或临时文件 | 高 | typed payload、URI allowlist、无自定义 header、过期清理 |
| 创作 UI 被软键盘/大字体遮挡 | 中高 | 安全区、键盘避让、200% 字体和横竖屏设备验收 |

## 16. P4 完成定义

P4 只有同时满足以下条件才能标注完成：

- P4-0～P4-7 全部实现并有验证文档；P4-8 完成实现或明确后置结论；
- 回答新建、编辑、想法发布和本地草稿恢复在 API 24 设备闭环；
- 图片选择、处理、单图/多图上传和失败恢复闭环，OSS 凭证不落盘；
- 视频前台播放、生产扫码和三类系统分享闭环；
- 发布失败、进程被杀、断网、会话失效和账号切换均不丢失或串用草稿；
- API 26 编译与 API 24 兼容完整构建成功，全部 Hypium 新鲜通过；
- 没有新增未保护的 API 26-only 调用、无不必要权限、无 Cookie/草稿/凭证日志；
- P3 与 P4 的返回栈、滚动恢复和登录恢复没有回归；
- `docs/harmonyos-migration-plan.md`、测试基线、CI 和功能矩阵同步更新；
- Git 工作区干净，已合并 worktree/feature 分支已清理，所有提交保持本地且未 push。
