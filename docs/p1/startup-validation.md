# P1 AppStartup 与日志基础设施验证

## 目标

在 API 24 基线上建立可扩展的启动依赖图，使关键初始化可以在首页加载前等待，非必要初始化只能在首页加载成功后执行。启动诊断只记录固定事件、任务状态和耗时，不记录 Cookie、原始 URL、账号、异常消息或响应内容。

## 初始化图

```text
deep-link-routing (critical)
        |
        +-- 首页 loadContent 成功
                    |
                    +-- app-ready-diagnostic (deferred)
```

- `EntryAbility.onCreate()` 创建图并立即启动关键阶段。
- `onWindowStageCreate()` 等待同一个关键阶段 Promise；关键节点失败时不加载首页。
- `loadContent()` 成功回调才触发延迟阶段，页面加载失败不会启动非必要任务。
- 同一阶段的重复调用复用首次 Promise，任务不会重复执行。

## 编排契约

- 任务名必须是稳定的 ASCII 标识，且全图唯一。
- 所有依赖必须存在；关键任务不能依赖延迟任务；循环依赖在构图时拒绝。
- 同时满足依赖的任务按名称排序，保证注册顺序变化时执行顺序仍然确定。
- 关键阶段任一失败或跳过都会使阶段失败，并阻止整个延迟阶段。
- 延迟任务失败后只跳过依赖它的节点；无关节点继续运行，阶段标记为 `degraded`，错误不抛回首页。
- observer 仅用于诊断；observer 自身失败不会改变启动结果。

## 日志安全

`AppLogger` 不提供任意字符串日志入口。业务侧只能提交固定 `AppLogEvent`，失败日志额外只接受数值错误码。启动摘要字段限定为：

- 阶段与阶段状态；
- 代码中声明的稳定任务名；
- 任务成功、失败或跳过状态；
- 阶段和任务耗时（毫秒）。

深链日志只区分“已解析”和“不支持”，不记录目标类型、原始 URI、内容 ID 或查询参数。页面加载失败不再序列化系统异常对象，只记录错误码。

## 自动化覆盖

`AppStartup.test.ets` 覆盖：

1. 依赖顺序确定且耗时摘要可重复断言；
2. 关键与延迟阶段重复启动幂等；
3. 延迟任务失败与无关节点隔离；
4. 关键任务失败后延迟阶段整体跳过。

本任务按并行开发边界只完成代码与静态自审，不单独修改测试聚合入口，也不运行全量构建或模拟器。主任务合并各 P1 子任务后统一接入测试套件，并以 API 24 工具链执行构建与 Hypium 验证。
