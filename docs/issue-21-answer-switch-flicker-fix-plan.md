# Issue #21：左右切换回答闪屏修复方案

制定日期：2026-10-27。状态：**已开始实施，完整修复尚未完成**。

实施进度：已将单篇切换改为先准备导航目标和详情、成功后再提交；等待或失败时保留当前正文和导航位置，过期结果及重复提交被拒绝。横向模式固定问题标题，并将仿制摘要改为局部占位。已接入双正文原型：候选按真实尺寸挂载，视口与信息头布局就绪后提交，候选成为当前正文时按同一键保留实例（尚未用生命周期日志确认）；隔离阅读位置、音量键及公式缓存清理。API 26 模拟器验证了 A→B→A 的内容、作者和已有阅读位置，但未采集过渡帧，也未验证弱网和设备矩阵。图片横滑切答与普通点击预览各验证一次。拖动时仍是占位，真实候选跟手动画和有限预取尚未实现，当前不能判定 Issue 已完整修复。

## 1. 结论与修复范围

建议采用 **固定问题标题和页面外壳、当前回答与候选回答双实例交接、相邻全文有限预取** 的方案。

闪白／闪黑的主要原因已经形成证据闭环：松手触发切换时，现有代码先清掉滑动预览，再清空当前详情；正文、信息头和底栏退场，整页变成主题背景上的加载提示，网络请求完成后再重新创建详情。这段空档在浅色和深色模式均已抓到。相邻页又是独立绘制的摘要，不能直接变成完整正文，进一步放大切换时的视觉差异。

本方案处理**单篇阅读的同一问题内左右切换**，不以默认开启连续阅读替代修复，不改为 WebView，不引入新路由栈。上一答、下一答、悬浮按钮及翻页越界入口需要共用同一个安全切换事务；纵向手势的触发条件、文章页、问题页和连续阅读模式保持原有语义并纳入回归。

## 4. 方案取舍

| 方案 | 评价 |
| --- | --- |
| 修改背景色、延长动画、加载提示淡入淡出 | 无法消除正文被移除的问题；不作为根治方案 |
| 只预取下一答全文 | 能缩短请求时间，但首次未命中、分页和失败仍会清空正文，摘要与实页也仍然不同；只能作为配套能力 |
| 固定外壳＋当前/候选真实正文＋提交后换身份 | **推荐**。保留旧答直至新答可显示，失败可回退，滑动中的正文与落地后的正文一致 |
| 用 Swiper 重写整个单篇页面，或替换为连续流 | 还需要处理懒加载、活动页、副作用、滚动恢复和手势冲突；不是仅换容器即可修复。本期不扩大到这类重写 |

可先落地“加载期间保留旧答、成功后交接”的最低修复，再补真实候选页的跟手动画和预取。最低修复可消除整页加载空档，但只有完成真实候选页交接及标题稳定验收后，才能宣称 #21 的完整体验问题得到解决。

## 5. 推荐实现设计

### 5.1 稳定页面外壳与标题

- 保留当前回答路由，不为每次横滑调用 `push/replace`；`contentId` 继续表示路由所有者，实际操作目标另用已提交的回答 ID。
- 同一问题的 HDS 返回键和问题标题只保留一份，不参与回答横向位移，也不切回整页加载标题。建议横向模式的固定顶栏始终显示问题标题；作者摘要在成功提交时更新。
- 现有正文内的大标题可以继续保留为阅读信息头，但它不是另一份导航栏；固定标题的文本、位置和可见性不能因切换回答而重置。纵向滚动折叠与横向切换分开处理，切换过程冻结标题几何，提交后再根据新正文位置更新作者等信息。
- 取消横向预览中的第二套标题栏和假底栏。底部操作栏只保留一个稳定容器，等待和滑动期间禁用回答相关操作，提交时一次性绑定新回答的统计与状态；返回入口始终可取消切换。
- HDS 树下继续使用 AppStorage 广播，并加入 `routeKey / questionId / sessionEpoch`，不能依赖普通 `@Builder` 参数更新已挂载标题。失活路由不得覆盖当前标题。

这会将横向模式从“整页跟手”调整为“回答区域跟手、问题标题稳定”，属于有意的交互变化，实施时需记录在修复说明中。

### 5.2 切换事务：准备与提交分开

新增独立的单篇回答切换状态层（建议 `AnswerSwitchState.ets`），避免继续把异步事务集中堆在页面组件中。至少维护：

- `committedAnswer`：当前实际显示、可操作的回答及阅读锚点。
- `candidate`：方向、目标 ID、详情、正文准备状态，不等同于当前回答。
- `switchToken`、会话代次、路由身份、账号身份、问题 ID：共同校验回包及动画完成回调。
- 状态：`idle → dragging → preparing → settling → idle`；取消和失败都回到旧回答。

| 阶段 | 处理规则 |
| --- | --- |
| 拖动 | 保留当前真实正文；候选已准备好则显示真实候选页，否则仅在露出区域显示明确的局部加载占位，不伪装成完整详情 |
| 松手未达阈值／系统取消 | 回弹原位，丢弃提交意图；不改导航索引，不记候选阅读历史 |
| 达到阈值但候选未就绪 | 当前正文保留；平滑回到稳定位置或保持有限预览，并显示局部“正在加载下一答”。首期建议回到稳定位置，避免长期半页悬停；加载成功后再完成一次交接 |
| 候选数据及视口准备就绪 | 真实候选进入滑动位置；完成位移动画时原子提交新回答、导航索引、作者与操作栏身份，再移除旧实例 |
| 加载失败、目标失效、分页失败 | 保持原回答和原锚点，显示局部错误／重试；不给旧正文配上新回答 ID |
| 返回、切换账号、切换阅读模式或路由失活 | 使 token 失效，停止派发及取消本会话请求；迟到回包、就绪和动画回调均不得提交 |

首期 `preparing/settling` 阶段只允许一个切换意图，重复手势和下一答按钮不叠加队列；未达阈值的候选请求可以作为本会话有限缓存，但不能触发阅读副作用。避免“快速划三次、数秒后自动跳三答”。

`QuestionAnswerNavigator` 需要增加类似 `prepareMove(direction)` 和 `commitMove(targetId, token)` 的两阶段接口：准备阶段可以加载分页、确认候选，但不改变当前索引；提交阶段再次验证会话、排序与候选身份。取消不回滚已经取得的合法分页数据，只撤销目标选择。沿用排序、过滤、去重和直达回答不在列表中的语义；过滤空页要设自动追页预算，耗尽时给出继续加载入口。

### 5.3 两个真实正文实例及就绪条件

抽出 `AnswerDocumentPane` 一类单答呈现单元，复用 `NativeContentDocument` 和现有信息头／正文块渲染。最多同时挂载当前答及一个候选答，不重新复制一套摘要排版。

1. 实例以 `sessionEpoch + answerId + contentRevision` 为稳定键；候选升为当前时只改变角色和位移，**不移到另一条会重建它的条件分支**。角色变化不能改变键。
2. 同一实例内的 HTML 和内容身份不可偷偷换成另一答；新答建立新实例。不要仅给 `html` 加 `@Prop` 就认为问题解决，内部数据源、选区、测量、链接卡片及进度均有生命周期。
3. 数据可用不等于可见区域已经准备好。增加携带候选 token 的 `onViewportPrepared`：解析完成、List 具有有效宽高、目标视口的头部／正文或合法空态已布局，并完成所需位置初始化。图片未下载完可保留尺寸占位，不等待所有远端资源。
4. 候选必须以正常尺寸参与布局；不能使用 `Visibility.None` 后等待布局回调。离屏或覆盖层方案是否仍执行懒加载，在 API 23/26 原型中验证。
5. 可以结合 `UIContext.postFrameCallback` 安排布局后的交接检查；本机 SDK 标注其及 `FrameCallback` 自 API 12 可用。`onFrame` 是帧开始回调，`onAreaChange` 是几何变化信号，都不能单独证明最终像素已经显示。最终仍要用画面与性能轨迹验证，不能写死 `setTimeout(200)` 假定准备完成。
6. 设置准备超时；超时保留旧答并提供重试，不允许永久锁住页面。

旧实例的销毁也需检查：当前 `NativeContentDocument.aboutToDisappear()` 会保存位置、清理链接元数据加载器并调用全局 `clearFormulaByteCache()`。双实例共存后必须确认这些清理不会影响候选页；有共享资源的改为会话级管理或明确的引用生命周期。

### 5.4 预取、缓存与请求隔离

- 当前答稳定后优先准备下一答；上一答优先使用刚读过的缓存。候选来自现有导航器顺序，不另建一套回答排序。
- 初始预算建议：当前答＋前一答＋后一答，最多 3 份全文数据；最多 2 个正文 UI 实例；后台全文预取并发 1。全文体积另设预算，经长回答原型测量确定，不能只限篇数而不限内存。
- 预取与用户请求同一回答时复用在途任务和结果；主动切换优先于后台请求。缓存淘汰时释放 HTML、解析块及重资源，禁止累积成全问题全文缓存。
- `ZhihuHttpClient` 存在单实例单飞约束；新增会话级独立详情仓库／client，分页沿用自己的仓库。不能让预取占住 `Index.ets` 当前共享 `answerRepository` 而阻塞前台详情或相互取消。
- 可参考 `ContinuousAnswerRepositories.ets` 和 `ContinuousFullTextScheduler` 的请求槽隔离、去重与有界缓存思路，但不直接共享连续流会话。现有调度器离页允许部分在途结果落账，接入单篇事务前必须补齐 token、账号及问题校验。
- 缓存键至少包含账号／会话、问题、回答及数据版本；登出、账号变化、排序／过滤变化时失效相关候选。互动后的当前状态不能被旧缓存的投票、收藏计数覆盖。

### 5.5 副作用与阅读位置

这是双实例方案的必要前提，不能留到最后补丁处理。

- 预取只调用详情获取能力，不调用带阅读记录副作用的 `ContentDetailController.load()`。复用已抽出的 `recordContentOpen()`，仅在真实切换提交后记录一次，不等待历史写入完成才解除动画锁。
- 为正文补充显式、可更新的活动状态。当前 `positionIsActive()` 只判断路由所有者；两个正文共用同一路由时会同时判活。候选布局准备与“用户正在阅读”的身份必须分开，候选不持久化进度、不响应翻页／音量键、不抢选区、不广播折叠标题。
- 切换前保存当前实际回答的锚点；失败／取消保留旧位置；候选的恢复只读取候选自己的 `answer:<id>`。源码目前会读取已存位置，不能仅凭 `moveAnswer()` 中“从顶部渲染”的注释就删除恢复能力。方案保留已有位置恢复，无有效位置才从顶部开始。
- 返回已缓存回答时恢复该答锚点；切换完成后的边界信号来源必须匹配新实例，沿用并扩展 `acceptsContentDocumentEvent()` 的代次防护。
- 投票、收藏、评论、段评、分享、朗读及图片／链接操作绑定事件来源的回答 ID。等待期间不提前变更 `activeContentId`；提交后再切换控制器，旧请求完成也只能回写其原目标。
- 新实例的活动状态要能在不重建实例的情况下生效；普通字段不适合承载此变化。正文宿主使用适合当前 ArkUI 树的可观察属性，HDS 跨树状态继续走带身份的 AppStorage 通道。

## 7. 验证计划与验收标准

### 7.1 自动化测试

优先扩展 `QuestionAnswerFeed.test.ets`、`ContentDetailState.test.ets`，新增切换事务测试并注册到 `List.test.ets`：

- 在途、失败及取消期间，当前内容／导航 ID／阅读记录不变；成功后只提交一次。
- A→B 失败后再次下一答仍是 B，不跳到 C；分页失败、末页、过滤空页和直达目标不在种子中保持正确语义。
- 旧请求迟到、页面退出、账号切换、排序变化、过期准备回调及重复动画结束均不能覆盖新会话。
- 预取不记历史、不上传历史、不保存阅读位置；候选提交后副作用仅执行一次。
- 候选没有视觉准备回调时不卸载当前答；准备超时可恢复操作；数据缓存命中仍遵守视觉交接。
- 取消手势、连续快速操作、选词冲突、首尾边界及纵向触发逻辑不回归；跨答事件不会操作另一答。
- 缓存、并发、取消和旧实例清理有界；文章／问题的原加载及错误语义保持。

控制器测试不能证明画面无闪烁，必须配合以下设备验证。

### 7.2 设备矩阵

| 维度 | 用例与通过条件 |
| --- | --- |
| API／主题 | API 23 最低线、API 26；浅色、深色、跟随系统切换；均不出现只有背景与全屏加载提示的过渡画面 |
| 热／冷路径 | 预取命中、未命中、分页边界、模拟延迟、断网、403／401、目标删除；等待时旧答可见，失败可重试且索引不前移 |
| 手势 | 左右切换至少各 20 次，未过阈值回弹、反向拖动、系统取消、快速连滑；一笔手势最多提交一次，无结束后延迟连跳 |
| 标题与底栏 | 顶部及深度滚动后切换；问题标题不因横滑平移／消失／切回“回答”；新正文与作者、统计和操作目标同时生效 |
| 内容 | 短答、长答、图片、公式、引用、认可信息、链接卡片、划线；预览与落地为同一正文实例，无摘要转正文的整块替换 |
| 阅读状态 | A→B→A、历史位置、评论／个人页返回、后台恢复、连续／单篇模式切换；锚点属于正确回答，返回层级不变 |
| 交互隔离 | 候选不能投票／收藏／记历史／响应翻页，旧回包不污染新答；选词、图片预览和朗读与切换互斥规则可预期 |
| 资源与性能 | 连续切换 100 次后，全文记录数及正文实例数不突破预算；记录堆内存、首屏准备耗时及动画帧耗时，无随次数持续增长的泄漏 |

实施时记录切换意图、候选 ID 确定、详情返回、正文准备、提交五个时间点，按同一设备、同一内容比较优化前后 P50/P95。采集日志只含内容 ID、状态和耗时，不输出 Cookie 或正文。预取命中与未命中分开统计，避免用网络波动解释或掩盖 UI 空档。

官方[ArkUI 页面滑动卡顿丢帧问题分析](https://developer.huawei.com/consumer/cn/doc/doccenter-dev-faq/faqs-performance-53)将应用构建、布局、渲染服务和最终显示区分为流水线阶段；本方案据此要求画面取证与性能轨迹同时验证，不把单个生命周期回调当作最终显示完成的证明。

## 8. 完成判定

完整修复应同时满足：**旧正文不被提前清空、固定问题标题稳定、真实候选页无需再次重建、失败不推进导航、所有操作与阅读副作用绑定已提交回答**。只减少加载时间、只保留背景或者只让标题不闪，都不能单独作为关闭 #21 的依据。

参考既有工作：[同一问题下回答连续阅读计划](continuous-answer-reading-plan.md)。可复用其底层全文调度与渲染经验，但本方案针对保留的单篇模式，需独立验收。
