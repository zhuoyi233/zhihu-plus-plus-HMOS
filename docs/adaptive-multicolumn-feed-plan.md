# 自适应多栏信息流接入方案

日期：2026-10-24。

状态：第一、二阶段代码已实现（Hypium 917/917、Debug 构建通过）；设备验收尚未执行，
换列保位 `extraOffset` 方向等仍需真机/模拟器核实。

调研依据：[TiebaPura 自适应多栏信息流调研](./tiebapura-adaptive-feed-research.md)。

## 1. 目标与范围

在现有双列瀑布流基础上，支持随页面宽度自动切换 1～4 列，并配套卡片适配、分页补屏和换列保位。

覆盖首页、关注页的推荐与动态、热榜、日报。沿用 `HomeFeedPage` 与 `ChannelFeedPage`，保留现有 `WaterFlow + SLIDING_WINDOW + WaterFlowSections`。

本方案仅处理信息流内容多列。列表与详情并排的导航双栏另见 [平板双栏方案](./tablet-two-pane-plan.md)，两者独立；未来导航分栏后，信息流仍按其自身容器宽度计算列数。

实施分两阶段：

| 阶段 | 交付内容 |
| --- | --- |
| 第一阶段 | 自动 1～4 列、卡片适配、分页补屏、换列保位 |
| 第二阶段 | LazyForEach 懒加载、精细数据通知、列数设置与持久化 |

## 2. 第一阶段：自动多列

### 2.1 统一布局策略

在 `entry/src/main/ets/pages/FeedWaterfallLayout.ets` 增加统一布局计算函数，返回最终列数、可用内容宽度、卡片宽度、行列间距等参数。页面只消费结果，避免各自复制断点判断。

自动模式的初始断点建议如下，实施时通过设备效果确认：

| 页面宽度 W（vp） | 候选列数 |
| --- | --- |
| W < 600 | 1 |
| 600 ≤ W < 900 | 2 |
| 900 ≤ W < 1200 | 3 |
| W ≥ 1200 | 4 |

以上为拟定值，尚未完成视觉验收。按当前页面左右各 12vp、列间距 14vp 计算，在进入 2/3/4 列的边界，卡宽约为 281/283/284vp。

再用最小卡宽保护限制最终列数，常规字号可先以约 280vp 为起点：

    内容宽度 = 页面宽度 - 左右外边距
    可容纳列数 = max(1, floor((内容宽度 + 列间距) / (最小卡宽 + 列间距)))
    最终列数 = min(候选列数, 可容纳列数)
    卡片宽度 = (内容宽度 - (最终列数 - 1) × 列间距) / 最终列数

字号放大时提高所需最小卡宽，必要时减少列数；具体字号映射需结合系统字体缩放和本项目实际排版验证。单列页面不足最小卡宽时允许卡片占满可用空间。

测量口径必须统一：

- 使用实际页面容器的 vp 宽度，支持旋转、分屏、自由窗口和折叠变化。
- 当前 `feedWidthVp` 来自带页面 padding 的外层容器；若继续使用它，计算内容宽度时只扣一次外边距。若改测 WaterFlow 内容区域，不得再次扣除同一份 padding。
- 不用物理 display 宽度决定页面列数，不引入型号白名单。
- 仅宽度变化、列数与分组配置未变时，让框架自然重排宽度，避免重复替换 sections。

### 2.2 接入现有页面和分组

修改：

- `entry/src/main/ets/pages/HomeFeedPage.ets` 的 `rebuildFlowLayout()`。
- `entry/src/main/ets/pages/ChannelFeedPage.ets` 的 `rebuildFlowLayout()`。

将目前固定的 `width >= 600 ? 2 : 1` 替换为统一布局结果。关注的两个子页、热榜和日报共用 ChannelFeedPage，因此不需要另写各自的列数规则。

使用 `WaterFlowSections` 时，内容列数由 section 的 `crossCount` 决定；`columnsTemplate` 会被忽略。公告、错误提示、关注用户栏、日期标题和加载尾部继续作为单列通栏分组。

所有分组的 `itemsCount` 总和必须与真实 FlowItem 数量一致。数据、通栏项和加载状态更新时协调分组更新，避免只改数据或只改分组。

`usesCardSurface()` 改为依据“最终列数 > 1 或用户选择卡片样式”决定外观，使手动单列模式也能正确沿用用户样式。分组结构、计数、间距和列数均相同时不重复执行 `sections.splice()`。

### 2.3 卡片内部适配

首页卡片与 `components/FeedContentSummary.ets` 等共用内容组件使用同一布局口径：

- 标题保持最多两行；多列摘要可由三行收至两行，单列保持现有行为。
- 保持文字可读字号，通过减少列数、调整内容结构解决拥挤。
- 缩略图和文字区按真实卡宽分配空间，图片预留稳定尺寸，降低加载前后高度变化。
- 更多按钮及操作区域保留可点击空间，不被文本或缩略图挤出。
- 日报缩略图、标题与日期分组分别检查，不强套首页卡片结构。

最终列数和卡宽保存在每个页面本地，并通过组件参数传给卡片；不采用全局单值 `cardColumns`，避免离屏缓存页之间相互覆盖。

### 2.4 分页与首屏补足

同步修改 `FeedWaterfallLayout.ets`、`HomeFeedState.ets`、`ChannelFeedState.ets` 与两处页面的预取挂点：

1. `homeFeedInitialItemTarget()` 将固定的 `rows * 2` 改为实际列数；保留总目标上限和额外请求次数限制。
2. 可见索引预取从固定“剩余 3 条”改为按列数估算，例如保留两行内容的余量。
3. ChannelFeedPage 目前只有日报使用可见索引预取；对有分页能力的关注、热榜等来源补齐相同判断，已结束或不支持继续分页的来源不请求。
4. 数据或视口变化后补判内容是否不足一屏，覆盖过滤后条目稀少、宽窗首屏、单列切多列等情况。
5. 继续使用控制器的加载中、结束状态、请求代际和失活保护；补屏必须限次并防止重复游标循环，失败保留已有内容并允许重试。

沿用 `onScrollIndex` 与 `feedFlowItemIndex()`，以内容索引判断预取。SLIDING_WINDOW 下跳转或更新后的总偏移可能是估算值，不直接移植 TiebaPura 的“估算总高减 currentOffset”公式。

### 2.5 换列保留阅读位置

换列前记录首个可见内容的稳定身份；换列布局完成后，将该内容映射到新的 FlowItem 索引并恢复可见位置。过滤或删除使锚点消失时，优先选择仍存在的相邻内容；没有可用内容时回顶。

第一阶段以“原阅读内容仍可见”为验收目标；精确到卡片内部像素的偏移恢复，须核对 API 能力并完成真机验证后再纳入承诺。

- 旋转和窗口缩放不触发刷新，不主动清空列表或回顶。
- 只有列数变化时才启动必要的保位流程，避免同列数连续缩放反复跳转。
- 高频尺寸回调合并处理；正在拖动或惯性滚动时避免程序跳转与用户手势竞争。
- 公告、日期标题、页尾会改变 FlowItem 索引，恢复时走身份与分组映射，不能复用旧裸索引。
- 各页面分别保留锚点和 Scroller；离屏页在重新激活后使用最新布局偏好。

## 3. 第二阶段：懒加载与列数设置

### 3.1 将 ForEach 替换为 LazyForEach

SLIDING_WINDOW 优化布局计算范围，LazyForEach 优化按需创建节点，两者配合使用。保留现有布局模式，为首页和频道页设计可复用的数据源适配层。

建立统一的渲染条目模型，协调内容、日期、通栏项和加载状态的身份及数量；数据源通知与 sections 采用同一份布局快照。初步可新增 `FeedFlowDataSource.ets`，接口命名在实施时按现有代码风格确定。

数据同步至少区分：

- 尾部追加：核对旧内容前缀，通知范围完整覆盖实际新增条目。
- 单项更新：身份和顺序不变时通知对应项，避免整体重载。
- 删除或过滤：更新条目、索引映射和分组计数，保持锚点可恢复。
- 全量刷新或顺序变化：明确重载语义，不能只按数组长度判断追加。

使用稳定的内容身份键，单独处理内容更新通知。现有 `QuestionAnswerDataSource` 可以参考 IDataSource 接口结构，但它只有全量 replace，不能直接满足信息流增量更新需求。

完成懒加载后，再配置按列数增长的 `cachedCount`；可从 `max(5, columns * 2)` 起步，结合卡片构建耗时和内存调整。普通 ForEach 上仅设置 cachedCount 不会获得同样的按需创建效果。

### 3.2 用户列数设置

在外观设置的“信息流”区域增加“信息流列数”：

    自动 / 单列 / 双列 / 三列 / 四列

默认“自动”。手动列数表示期望值，实际列数仍受可用宽度与最小卡宽保护，空间不足时减少；设置说明应明确这一点。

接入位置：

- `data/src/main/ets/preferences/AppPreferencesStore.ets`：增加类型、默认值、非法值归一化和持久化。
- `data/Index.ets`：按需导出新类型或工具函数。
- `entry/src/main/ets/pages/AppShell.ets`：冷启动读取并广播偏好。
- `entry/src/main/ets/pages/AppearanceSettingsPage.ets`：复用现有选择控件与保存流程。
- HomeFeedPage、ChannelFeedPage：通过 AppStorage + `@StorageProp` + `@Watch` 接收偏好，每页独立计算最终布局。

沿用已有跨页信号机制，不依赖 HdsTabs 下未可靠链接的 Provide/Consume。全局只广播偏好，不广播所有页面共用的最终列数。

新增控件跟随 `resolvedThemeColor`，主操作文字色使用 `onThemeColor`。旧用户没有保存值时回退自动模式，其他外观偏好保持原值。

手动切换列数默认复用换列保位机制；如后续决定改为切档回顶，应单独明确交互并补充验收，避免照搬上游回顶行为。

## 4. 验证与交付

### 4.1 自动化验证

扩展现有 `FeedWaterfallLayout.test.ets`；增加有实际行为价值的测试：

- 600/900/1200vp 断点前后、最小卡宽限制、异常或尚未测得的尺寸。
- 不同列数的首屏目标与上限；图片或长文本不参与错误的固定高度布局。
- 日期、公告、页尾动态变化时分组计数与内容索引映射正确。
- 内容删除、过滤和换列后，稳定身份对应的恢复位置正确。
- 分页补屏限次、重复游标、旧请求返回与页面失活。

第二阶段再补数据源追加多条、刷新后变长、更新、删除等通知行为，以及列数偏好的默认值、归一化和持久化兼容性。测试注册遵循现有 List.test.ets，不手动维护测试总数。

### 4.3 设备验收

基础回归使用默认 API 23 模拟器 ZhihuPlus_API23；宽窗口验收还需要可覆盖平板、折叠或自由窗口的测试目标。实际测试时记录设备、系统版本和页面实测 vp 尺寸。

| 场景 | 验收重点 |
| --- | --- |
| 手机窄窗 | 单列布局、主题色、菜单和点击区域正常 |
| 平板竖屏约 711vp | 自动双列，内容和通栏项正常 |
| 平板横屏约 1138vp | 自动三列，已有阅读内容仍可见 |
| ≥1200vp 宽窗 | 四列下摘要、缩略图和操作区可读可用 |
| 临界宽度来回缩放 | 列数正确、不循环重建、不意外刷新 |
| 长列表中旋转或折叠 | 锚点不跳到无关内容，无整片空白或滚动失效 |
| 不同数据状态 | 公告出现/消失、日报跨日期、加载尾部均通栏且计数匹配 |
| 分页与过滤 | 首屏补足、触底继续、屏蔽删除后补屏，不重复请求 |
| 图片与大字号 | 图片加载前后位置稳定，最小卡宽保护有效 |
| 切页与返回 | 各页列数、分页游标、滚动位置彼此独立 |

性能测试使用同设备、同数据量、相同滚动操作对比，记录掉帧与内存；不引用上游测量替代本项目结果。
