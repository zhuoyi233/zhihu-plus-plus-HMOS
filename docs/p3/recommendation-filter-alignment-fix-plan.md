# 推荐系统与内容过滤对齐修复计划

> 制定日期：2026-09-16  
> 鸿蒙基线：`dev` / `2b3ed0850d1f5490ada736a865e1df50e6df7507`  
> Android 上游基线：`refs/remotes/upstream/master` / `b68cd3ad6dd53c0d4adf5142f47cede1bb28e594`  
> 验证环境：HarmonyOS API 26 编译，`targetSdkVersion=26.0.0`，`compatibleSdkVersion=6.1.0(23)`

## 1. 目的与结论

本计划处理「推荐系统与内容过滤」设置页已经具备 UI 和持久化，但部分运行时语义没有完全对齐 Android 上游的问题。

当前 Web、Android、混合推荐源、登录推荐、启动缓存、质量阈值、智能曝光过滤、精确规则、推广/付费过滤、反向屏蔽和统计入口均已接入生产代码，不属于静态占位页；但仍存在以下必须修复的差距：

1. 「本地推荐」只是缓存/网页候选的热度排序，不是上游本地行为推荐引擎；
2. 非首页 Repository 使用缺省推荐过滤配置，导致用户设置与实际过滤结果不一致；
3. 关键词规则不匹配正文；
4. 用户规则不匹配问题提问者；
5. 切换推荐模式后首页不主动刷新，旧游标可能与新模式冲突；
6. 运行时 RDB、设置页到组合根的集成缺少自动化覆盖。

在这些问题修复前，该功能应标记为「核心链路可用、部分对齐」，不得宣称与上游完整一致。

## 2. 目标行为边界

修复前先冻结作用域，避免把所有过滤策略无差别扩散到所有列表：

| 能力 | 目标作用域 | 说明 |
| --- | --- | --- |
| Web / Android / 本地 / 混合推荐 | 首页 | 决定首页数据源 |
| 推荐时登录、启动时自动刷新 | 首页 | 控制首页请求凭证和启动快照 |
| 质量过滤、智能曝光过滤 | 首页 | 对齐上游 Home Feed 流水线 |
| 推广、付费、反向屏蔽 | 首页 | 反向屏蔽明确只改变首页 |
| 关键词、用户、主题精确规则 | 首页、关注、热榜、日报、搜索内容、问题回答 | 所有已经接入 `ContentBlockingMatcher` 的内容流 |
| 屏蔽记录 | 所有发生实际屏蔽或用户主动屏蔽的入口 | 只保存有稳定内容身份的数据 |

NLP/语义关键词过滤仍属于端侧 AI 能力，本批不实现。当前 Android 上游运行时保留语义过滤，但设置页没有对应的独立可见开关；鸿蒙端必须在发布说明中明确该能力差距，不得把精确关键词匹配描述为语义过滤。

## 3. 问题清单与修复设计

### RF-01 非首页过滤器错误使用推荐默认值（P0）

**现状**

- `entry/src/main/ets/pages/Index.ets` 为首页构造了带推荐偏好和运行时的 `homeBlockingMatcher`；
- 关注、热榜、日报、搜索和问题回答使用只传规则与规则偏好的 `blockingMatcher`；
- `BlockingRuleMatcher.createSession()` 在没有 `RecommendationFilterPreferencesGateway` 时自动使用 `defaultRecommendationFilterPreferences()`；
- 因此非首页内容流仍会按默认值屏蔽广告、学堂、微信外链和盐选，用户关闭对应开关也无法控制这些页面。

**修复**

1. 删除「未注入推荐偏好时自动启用默认推荐过滤」的隐式语义；
2. 将 session 明确拆为两种策略：
   - `RULES_ONLY`：只执行用户、关键词、主题规则；
   - `HOME_FULL`：执行首页推荐过滤，再按既有优先级执行精确规则；
3. 生产组合根显式构造两种 matcher，不允许依赖构造参数缺失来推导行为；
4. 保持单批只加载一次不可变规则/偏好/RDB 快照；
5. `reverseBlock` 或已关注作者旁路只影响 `HOME_FULL`，不能跳过非首页的精确规则。

**验收**

- 关闭任一推广过滤开关后，首页下一次刷新按新值生效；
- 非首页不再偷偷使用推广过滤默认值；
- 关键词、用户、主题规则仍在所有已接入内容流生效；
- 新增组合根测试，断言所有生产 Repository 获得正确 matcher 策略。

### RF-02 本地推荐不是上游本地推荐引擎（P1）

**现状**

`DefaultFeedRepository` 的本地模式读取启动缓存；没有缓存时拉取 Web 推荐，然后按赞同、关注、回答和评论字段做固定排序。它没有本地候选库、行为画像、抓取任务、推荐原因和点击反馈。

**短期止损**

- 在完整引擎交付前，将选项文案改为「本地排序（实验性）」并说明候选仍来自已有缓存或 Web；或者临时隐藏该选项；
- 不得继续使用「基于本地数据的推荐算法」「行为只在本地学习」等尚未成立的描述。

**完整修复**

1. 在 `data` 模块新增本地推荐 RDB 表：候选、抓取任务、抓取结果、行为记录；
2. 实现确定性的 `LocalRecommendationEngine`：候选收集、行为画像、评分、多样性、推荐原因；
3. 用户打开、点赞、不感兴趣和主动屏蔽写入本地行为，不上传为推荐特征；
4. 冷启动允许从关注推荐、热门和 Web 推荐补充候选，但必须保存来源和原因；
5. 本地模式只展示引擎生成的结果；候选不足时显示明确冷启动状态，不伪装为已完成的个性化推荐；
6. 清理任务遵循项目后台策略：只在前台或用户触发刷新时运行，不申请后台常驻。

**验收**

- 相同行为记录和候选集产生确定性排序；
- 打开/点赞/屏蔽能改变后续排序或候选可见性；
- 每条本地推荐具有稳定身份和可展示原因；
- 本地模式无网络时能使用已落库候选；
- 不复用 Web/Android 游标，不把本地分页伪装成远端分页。

### RF-03 关键词规则漏检正文（P0）

**现状**

`BlockableContentSummary` 已包含 `content`，但 `matchBlockingRules()` 只检查 `title + excerpt`。Android 上游会检查标题、摘要和正文。

**修复**

1. 匹配文本改为标题、摘要、正文三部分的有界拼接；
2. 总长度继续受 `MAX_BLOCKABLE_TEXT_LENGTH` 限制，避免超长 HTML 或正则放大计算成本；
3. 正文是 HTML 时，在 Repository 解码层尽量提供可见文本；若暂时只能提供原始 HTML，普通关键词仍可匹配，后续再统一接入安全文本提取；
4. 保持安全正则子集、大小写语义和固定屏蔽原因不变。

**验收**

- 关键词只出现在正文时也能命中；
- 关键词跨字段边界不会意外拼接成命中；
- 超长正文被确定性截断；
- 非法/高风险正则仍被拒绝。

### RF-04 用户规则缺少问题提问者维度（P0）

**现状**

鸿蒙 matcher 只比较 `authorId`。Android 上游还会比较回答所属问题的提问者，设置说明也包含「由特定用户提出的问题」。

**修复**

1. 为 `BlockableContentSummary` 增加可选 `questionAuthorId` / `questionAuthorName`；
2. Feed、问题回答等解码路径从真实 question author 字段传入，不使用作者名猜 ID；
3. 用户规则匹配顺序保持：内容作者优先，问题提问者其次，随后关键词和主题；
4. 屏蔽记录使用固定分类，并区分「屏蔽作者」和「屏蔽提问者」原因；
5. 设置页描述恢复为上游语义。

**验收**

- 被屏蔽用户发布的内容被过滤；
- 其他作者回答该用户提出的问题时也被过滤；
- 缺少 question author 字段时安全降级，不按名称误判；
- 用户开关关闭后两种匹配都停止。

### RF-05 设置变更没有驱动首页刷新（P0）

**现状**

设置保存后会增加 `contentFilterSettingsTick`，但首页没有订阅。页面返回前台时复用原控制器，列表和游标仍属于旧推荐模式；继续加载更多可能触发 `INVALID_CURSOR`。

**修复**

1. `HomeFeedPage` 使用 `@StorageProp('contentFilterSettingsTick') + @Watch` 订阅信号；
2. 信号触发时调用 `HomeFeedController.refresh()`，复用项目规定的 AppStorage 跨页面广播方式；
3. Repository 首屏刷新必须清空 `requestedCursors`、已交付身份集合和混合源游标；
4. 连续保存多个设置时允许合并刷新，控制器 inactive 时按既有约定 no-op，返回后由一次显式刷新恢复；
5. 保存失败不得广播刷新信号。

**验收**

- Web → Android → 混合 → 本地切换后返回首页自动重载；
- 不会拿旧模式游标请求新模式；
- 过滤开关/阈值改变后当前列表经刷新得到新结果；
- 快速连续修改不会形成并发刷新或迟到状态覆盖。

### RF-06 运行时统计与测试覆盖不足（P1）

**现状**

- `ContentFilterRuntimeStore` 负责曝光次数、打开历史、过滤记录、清理和统计，但没有独立 RDB 测试；
- schema 中存在 `content_filter_stats`，当前实现不读写该表，统计由曝光表和最近 500 条屏蔽历史临时计算；
- 设置页、AppStorage 信号、生产组合根和首页刷新之间没有端到端测试。

**修复决策**

二选一并在实现中保持一致：

1. 删除未使用的 `content_filter_stats` 表，把 UI 文案定义为「当前保留记录统计」；或
2. 正式维护累计统计行，使删除/裁剪屏蔽历史不会改变累计过滤数。

推荐采用方案 1，语义简单且与上游按当前记录计算统计的实现接近。若产品确实需要累计值，再采用方案 2 并增加迁移。

**验收**

- 曝光计数、第三次未打开过滤、打开后旁路、清理和清空都有 RDB 测试；
- 同一批过滤结果只 flush 一次，不重复累计；
- 统计文案与数据保留策略一致；
- schema 不保留无读写方的表。

### 9.2 验收中发现并修复的缺陷

**ContentFilterSettingsPage 异步加载竞态（回显固化）**：`restore()` 异步加载完成前表单已按
默认值首渲染，`@Builder` 按值传参把默认值固化，重进页面后 Select 永远显示「混合推荐」
（保存/持久化/首页刷新链路本身正常——preferences 文件与首页行为均验证无误）。
